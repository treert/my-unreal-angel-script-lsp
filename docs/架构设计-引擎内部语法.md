>

## 1. 通配类型 `?`

### 1.1 是什么

- `?` 是**只能在 C++ 注册串里出现**的"任意类型"形参标记，脚本作者永远不能在 `.as` 里声明它；
- 原版 SDK 要求写成 `?&in` / `?&out`，UE fork 放宽为也接受裸 `?&`（如 `Bind_UObject.cpp` 的
  `void opCast(?& Address) const`）；
- 它不是脚本语法，但 `.d.as` 导出声明里会大量出现，所以 tree-sitter 文法必须认识它。

### 1.2 `.d.as` 中的形态（已确认接受）

导出器（`TypeDeclarationExporter.cpp` 的 `ttQuestion` 分支）与 DebugServer（`AngelscriptDebugServer.cpp`
发送 `"type": "?"`）行为一致：**统一输出裸 `? ParamName`，丢弃 `&` 及方向信息（`&in`/`&out`）**。

决策：接受该失真，不做保真改造。理由：

- 脚本侧本来就不能写 `?` 类型，LSP 无消费 `?&out` 方向信息的场景；
- 保持与 DebugServer / 旧 LSP 输出的逐字节一致，方便行为对照。

全量语料约 20+ 处，典型：`FString.opAdd/opAddAssign/Append/Format`、`FText.Format`、
`DataTable.GetRow/AddRow/GetAllRows`、`GetAllActorsOfClass`、`FJsonObjectConverter.*`、
`FInstancedStruct.Make`。

### 1.3 文法层（已完成，勿重复处理）

- `grammar/grammar.js`：`wildcard_type` 规则（独立节点，不复用 `auto_type`）；
- `grammar/test/corpus/declarations.txt`：`void WildcardParameter(? Address) const;` 快照；
- 414 个 `.d.as` 零 ERROR 验收即包含此项。

### 1.4 语义层约定（as-core，P3 实现时执行）

| 环节 | 约定 |
|---|---|
| TypeRef | 增加 `Wildcard` 变体。**与 `auto` 严格区分**：`auto` 是用户可写的声明侧推导占位，`?` 是形参位的"匹配任意"，不得复用同一表示 |
| 重载解析 / 实参检查 | `?` 形参匹配任意实参类型，候选**排序最低**（避免遮蔽具体重载，如 `FString.opAdd(?)` vs `opAdd(FString)`） |
| hover / signatureHelp | 原样渲染 `?`，无特殊处理 |
| 默认值 | 引擎侧 `?` 参数均无默认值，无需处理 |
| 诊断（P5） | `?` 仅允许出现在 `.d.as` 形参位；用户 `.as` 中出现即报错（语义诊断 P5 按需设计，见[对比文档](../as-docs/原版AngelScript与UE-fork对比.md)） |

### 1.5 `opCast(?&)` 补充说明

`UObject.opCast(?& Address) const` 是编译器级的 universal cast 钩子，由 `cast<T>(Obj)`
显式转换触发，脚本不会直接调用它。

决策：**导出端不过滤、LSP 侧不硬性隐藏**（语法合法、与 DebugServer 输出一致）。
后续若成员补全里这个签名造成困扰，在补全排序中对"名为 `opCast`/`opImplCast` 且含 `?` 形参
的方法"降权即可，不改数据源。

## 2. `auto`（对照条目）

用户可写的推导占位，仅允许出现在局部变量与 range-for 迭代器声明位（BNF 注记）。
与 `?` 的区别见 §1.4——两者都在 `DATATYPE` 产生式里，但语义角色不同，节点与 TypeRef 表示均分开。

`auto` 的推导链（`this` 定型、链式访问、range-for `Iterator()/Iterate()` 双跳协议、失败降级）
见 [`LSP实现规划.md`](LSP实现规划.md) §4.2（引擎取证：`[ENGINE]as_compiler.cpp:5745-5873`）。

## 3. `unresolved_object`

### 3.1 是什么

- 类型名的**标记后缀**（BNF：类型后缀位 `{ ( '[' ']' ) | 'unresolved_object' }`），由 C++ 绑定层的
  `FObjectPtrType` 在**成员变量声明模式**下生成：`T unresolved_object`
  （`[UE]Private/Binds/Bind_BlueprintType.cpp:1854-1872`，`IsUnresolvedObjectPointer()` 标记，
  告知 AS 编译器该成员按 TObjectPtr 解析）。
- 脚本作者不书写它；它出现在 C++ 注册串与 `.d.as` 导出的成员声明里，典型：
  `FLatentActionInfo_.Property("UObject unresolved_object CallbackTarget", ...)`
  （`[UE]Private/Binds/Bind_FLatentActionInfo.cpp:23`）。
- 文法层已完成：`grammar.js` 的 `unresolved_object` 可选项 + corpus `types.txt` 快照
  （`UObject unresolved_object Marker;`）。

### 3.2 语义层约定（as-core）

| 环节 | 约定 |
|---|---|
| TypeRef | **不设新变体**：语法层记 flag；推导、成员补全、重载匹配一律按**基类型**（如 `UObject`）处理 |
| hover / signatureHelp | 原样渲染后缀，无特殊处理 |
| 诊断（P5） | 用户 `.as` 中出现该后缀属异常形态，占号归 `AS09xx`（引擎无对应报错，非引擎行为复刻，见[诊断码表](诊断码表.md)） |

与 `?`（§1）、`auto`（§2）、模板声明头（§4）同属「引擎内部语法」四件套，
总览见 §5。

## 4. 模板声明头（`struct TArray<T>` / `class TMap<K, V>`）

### 4.1 是什么

`.d.as` 里大量出现的 `struct TArray<T> { ... }`，**不是**引擎支持的脚本语法，而是
**我们的导出器渲染出的文本**。引擎从不读 `.d.as`。

AS 有**两条互不相通的解析入口**，模板声明头只走注册串那条：

| | 脚本文件路径 | C++ 注册串路径 |
|---|---|---|
| 入口 | `ParseScript` → **`ParseClass`** | **`ParseTemplateDecl`** |
| 位置 | `[ENGINE]as_parser.cpp:3734` | `[ENGINE]as_parser.cpp:176` |
| 调用方 | 编译 `.as` 模块 | `asCScriptEngine::RegisterObjectType`（`as_scriptengine.cpp:1719`） |
| 认 `<T>` | ❌ 标识符后只接受 `;` / `:` / `{`（`:3774-3810`） | ✅ 标识符后**必须**是 `<`（`:189-194`） |
| 认类体 `{...}` | ✅ | ❌ 必须 `ttEnd` 收尾（`:226-232`） |

数据源（`class` 关键字可选，故 `T` 与 `class T` 都收）：

```cpp
// [UE]Private/Binds/Bind_TArray.cpp:1338
auto TArray_ = FAngelscriptBinds::ValueClass<FScriptArray>("TArray<class T>", Flags);
```

导出侧从 `GetSubTypeCount()` / `GetSubType(i)->GetName()` 反查后拼成 `<T>`
（`TypeDeclarationExporter.cpp:526-533`）。

**关键结论**：`struct TArray<T> { ... }` 这个**完整形态**（声明头 + 类体）在引擎的
任何入口下都不合法——`ParseClass` 不认 `<`，`ParseTemplateDecl` 不认 `{`。
它**只在我们自己的 `.d.as` 方言里合法**。语言侧的完整取证与替代方案见
[`设计取舍与使用限制.md` §2.5.1](../as-docs/设计取舍与使用限制.md#251-脚本侧不能定义模板只能用-c-注册的)。

### 4.2 文法层（已完成并实测，勿重复处理）

- `grammar.js`：`class_declaration` / `struct_declaration` 的可选字段
  `type_parameters`（`:163`、`:178`），规则体 `'<' commaSep1(alias($.identifier, $.type_parameter)) '>'`（`:190-194`）；
- **实测零 ERROR**（2026-09）：`struct TArray<T>`、`struct TMap<K, V>`、
  `class TSubclassOf<T>`、以及特化块 `class TArray<FVector>` 四种形态全部正常建树；
- 模板**实例**（`TArray<FVector> Arr;` 这类使用位）走的是另一个规则
  `template_type`（`:496-499`），与声明头的 `type_parameters` 是不同节点，不要混淆。

### 4.3 语义层约定（as-core）

| 环节 | 约定 |
|---|---|
| TypeRef | 声明头里的每个 `type_parameter` → `TypeKind::Param(下标)`。**只可能来自 `.d.as`**：`.as` 源码索引路径永不产生 `Param`，可在该路径上直接断言 |
| 模板实例化 | 输入恒为「`.d.as` 的定义 + `.as` 侧的具体实参」，不存在脚本侧定义参与单态化（[LSP实现规划](LSP实现规划.md) §3.3） |
| **特化块消歧** | `type_parameter` 节点**同时承载**「类型形参 `T`」与「具体实参 `FVector`」（语法层无法区分，实测已确认）。按**声明前是否有 `@templateSpecialization` tag** 判定：有 → 块内名字是具体类型，该 class 是对既有模板实例的方法追加；无 → 是类型形参声明。**文法无需改动** |
| hover / signatureHelp | 声明头原样渲染 `TArray<T>`；实例渲染替换后的实参 |
| 诊断（P5） | 用户 `.as` 中出现模板声明头 → 引擎是 parse error。**是否报诊断按需决定**（D22），素材已登记于[诊断码表 §2](诊断码表.md) 末段 |

## 5. 四件套总览

| # | 构造 | 出现在 | 脚本可写 | TypeRef 表示 |
|---|---|---|---|---|
| §1 | `?` 通配类型 | `.d.as` 形参位 | ❌ | `Wildcard` |
| §2 | `auto` | `.as` 局部变量 / range-for | ✅ | `Auto` |
| §3 | `unresolved_object` | `.d.as` 成员声明后缀 | ❌ | 基类型 + flag（不设变体） |
| §4 | 模板声明头 `<T>` | `.d.as` 类型声明 | ❌ | `Param(下标)` |

四者的共性是「**语法层已接受、但语义层需要专门约定**」；其中 §1/§3/§4 三项是
**`.d.as` 独有、`.as` 侧非法**——这正是「`.d.as` 不是 `.as` 的子集，而是与之**交叉**」
的具体内容（见 [`../grammar/README.md`](../grammar/README.md#as-与-das-的关系交叉不是子集)）。
