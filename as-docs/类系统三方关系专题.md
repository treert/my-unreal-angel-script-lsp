> 版本：v0.1
> 上游文档：[`设计取舍与使用限制.md`](设计取舍与使用限制.md)（§0「引擎同构语言」定位与两条第一性原则，本文是其类系统侧的运行时展开）

> - `[UEENGINE]` = `config.paths.unreal_engine`/Engine/Source/（**引擎本体，含 AS 分支补丁，`AS FIX` 标记**）
> - `[UE]` = `config.paths.unreal_engine`/Engine/Plugins/Angelscript/Source/AngelscriptCode/

> 注意 `[UEENGINE]` 与其他文档的 `[ENGINE]`（= .../Angelscript/ThirdParty/source/，AS 解释器源码）不同：本文讨论的是**引擎侧补丁**，取证集中在引擎本体。

## 0. 为什么单独成篇

「AS 介于 UE C++ 和蓝图之间」是常见的一句话概括，但它回避了所有实质问题：

- 蓝图可以继承 AS 类，AS 类却**不能**继承蓝图类——单向性写在哪、为什么？
- AS 类「不是 C++ 类型」，但它在引擎里到底是什么？蓝图系统如何消费它？
- 改一个 AS 类，蓝图侧发生什么？`reinstancing` 的完整代价？
- 手机上只推 `PrecompiledScript.Cache` 热更脚本，边界和限制在哪？

这些问题共享同一个底层模型（元类 + 引擎补丁 + 双执行模型），散在各处讲必然零碎，故独立成篇。
本文全部结论以引擎源码为准，其中引擎本体里的 `AS FIX` 补丁标记是 AS 分支魔改引擎的直接证据。

## 1. 元类模型：三个「类的类」平级并存

UE 采用元类（meta-class）模式：**每个类本身是一个 `UClass` 对象，而这个对象自己的类型（`GetClass()`）标识了它由哪个系统生成**。

```
UClass（native，C++ 编译期注册，反射安全）
├── UBlueprintGeneratedClass   ← 蓝图类
└── UASClass                  ← AS 类
```

取证：

```cpp
// [UEENGINE]Engine/Source/Runtime/Engine/Classes/Engine/BlueprintGeneratedClass.h:429
class UBlueprintGeneratedClass : public UClass, public IBlueprintPropertyGuidProvider

// [UE]Public/ClassGenerator/ASClass.h:11
class ANGELSCRIPTCODE_API UASClass : public UClass
```

两个易混点先纠正：

1. **不是「蓝图继承 UASClass」**——`UASClass` 与 `UBlueprintGeneratedClass` 是兄弟，不是父子。
2. **「AS 类不是 C++ 类型」指业务类**——`UASClass` 本体是 native 的 C++ 类，所以引擎能安全地对它做全部反射操作。同理 `UASFunction : public UFunction`（还有一个庞大的 JIT/参数形态特化子类家族，`ASClass.h:122-497`）。

| | 蓝图类 | AS 类 |
|---|---|---|
| 源载体 | `.uasset`（UBlueprint 资产） | `.as` 文本（编辑器）/ PrecompiledScript.Cache（cooked） |
| 编译产物 | `UBlueprintGeneratedClass` 实例 | `UASClass` 实例 |
| 元类本身 | C++ native | C++ native（相同） |
| `CLASS_Native` | 无 | 无 |
| `CLASS_CompiledFromBlueprint` | 有（本义） | **有（蹭的，见 §3.1）** |

## 2. 继承方向与硬边界

继承链方向是单向的：**C++ 类 ← AS 类 ← 蓝图类**。

- AS 类的父类：C++ native 类，或另一个 AS 类；
- 蓝图类的父类：C++ native 类、AS 类、或另一个蓝图类；
- **AS 类不能继承蓝图类**（下述三处证据环环相扣）。

### 2.1 证据一：类型绑定层只放行 native 类

```cpp
// [UE]Private/Binds/Bind_BlueprintType.cpp:988-990
// Only bind native classes
if (!Class->HasAnyClassFlags(CLASS_Native))
    return false;
```

`ShouldBindEngineType` 遍历 `TObjectRange<UClass>()` 决定哪些类注册进 AS 引擎。
蓝图类是 `BlueprintGeneratedClass`（运行时构造，无 `CLASS_Native`），在这一步就被过滤——
它根本不会成为 AS 类型系统里的一等公民（`TSubclassOf<>` 引用是另一条路，不算继承）。

### 2.2 证据二：预处理器超类解析只有两条出路

```cpp
// [UE]Private/Preprocessor/AngelscriptPreprocessor.cpp:2810-2893
auto SuperType = FAngelscriptType::GetByAngelscriptTypeName(ClassDesc->SuperClass);
if (SuperType.IsValid()) {          // 出路一：已绑定的 C++ 类
    ClassDesc->bSuperIsCodeClass = true;
    ClassDesc->CodeSuperClass = Class;
}
...
SuperClassDesc = GetClassDescFor(...);  // 出路二：另一个 AS 类
...
// 都不是 → 报错：
LineError(... TEXT("Class %s has an unknown super type %s."));
```

蓝图类两条路都进不去，编译期直接失败。

### 2.3 证据三：引擎侧 ShadowType 兜底

```cpp
// [UE]Private/AngelscriptManager.cpp:2974-2982
Data.ShadowType = Engine->allRegisteredTypesByName.FindFirst_CaseInsensitive(...);
checkf(Data.ShadowType != nullptr, TEXT("Unable to find C++ class %s to inherit from"), ...);
```

AS 类继承 C++ 类靠 shadow type 镜像内存布局（`PropertyOffset` 直接取父类
`GetPropertiesSize()`），该机制只对静态注册的 native 类型成立。

### 2.4 反方向：C++ 类可显式禁止被继承

```cpp
// [UE]Private/Preprocessor/AngelscriptPreprocessor.cpp:2829
if (Class->HasMetaData(CP_NAME_CannotDeriveAngelscript)) { /* LineError */ }
```

meta `CannotDeriveAngelscript` 让 C++ 类显式退出「可被 AS 继承」集合。

## 3. UASClass 的运行时形态

### 3.1 标志位组合（身份判定依据）

```cpp
// [UE]Private/ClassGenerator/AngelscriptClassGenerator.cpp:3180-3182
NewClass->ClassFlags = CLASS_CompiledFromBlueprint;   // 蹭蓝图的「非 native 类」通路
NewClass->bIsScriptClass = true;                       // 引擎补丁字段
NewClass->ClassFlags |= (SuperClass->ClassFlags & CLASS_ScriptInherit);
```

- 无 `CLASS_Native` / `CLASS_Intrinsic`；
- **借用 `CLASS_CompiledFromBlueprint`**：UE 引擎大量代码用该标志区分「非 C++ 编译的类」，
  AS 复用这条通路让蓝图继承、序列化、编辑器重建天然兼容；
- `bIsScriptClass` **是 AS 分支加进引擎本体的字段**，不是原版 UE 的：

```cpp
// [UEENGINE]Engine/Source/Runtime/CoreUObject/Public/UObject/Class.h:4025-4028
// AS FIX(LV): Runtime generated classes (angelscript)
TMap<FName, ASAutoCaller::FReflectedFunctionPointers> ASReflectedFunctionPointers;
void* ScriptTypePtr = nullptr;      // 指回 AS VM 的 asITypeInfo
bool bIsScriptClass = false;
```

同批补丁还加了 `ScriptTypePtr` 与 `ASReflectedFunctionPointers`。
`bIsScriptClass` 的准确语义是「**这个 UClass 由 Angelscript 运行时生成**」，
引擎侧拿它做热路径布尔判断（跳过脚本层找 native 祖先、绑定过滤等）；
与蓝图的区分则主要靠元类类型本身（`Cast<UASClass>` vs `Cast<UBlueprintGeneratedClass>`）。

**LSP 侧判定真值**：判断「这个类型是不是 AS 定义的」以 `bIsScriptClass` 为准。

### 3.2 内存布局是拼接的

- `ScriptPropertyOffset`：AS 属性从 native 父类 `GetPropertiesSize()` 之后开始排布（shadow type 机制）；
- `ContainerSize` + `GetContainerSize()` override：属性区实际大小；
- 属性由生成器逐个 `FProperty` 组装，非 UHT 生成；
- 热重载可用平台上属性区预留 +128 字节松弛（`ClassGenerator.cpp:3579-3582`，`#if AS_CAN_HOTRELOAD` 门控）。

### 3.3 生命周期与热重载

- 挂在 `FAngelscriptManager::GetPackage()` 专用包下，不在 `/Script/...`；
- 热重载时旧类改名 `XXX_REPLACED_N` 并打 `CLASS_NewerVersionExists`，
  `NewerVersion` 指向新类（`ClassGenerator.cpp:2562-2568`）；
- `GetMostUpToDateClass()` override 给引擎指路最新版。

### 3.4 行为桥接点

| 桥接 | 作用 |
|---|---|
| `UASFunction::RuntimeCallFunction/RuntimeCallEvent` | UE 反射调用 → 转发进 AS VM（或 JIT 入口） |
| `RuntimeDestroyObject` / `RuntimeAddReferencedObjects`（空实现） | AS 对象引用由 VM 侧管理 |
| `IsFunctionImplementedInScript()` | BlueprintNativeEvent 判断 native 侧是否有默认实现的依据 |
| `GetFirstASClass` / `GetFirstASOrNativeClass` | 沿 SuperStruct 链找第一个 AS 类 / native 祖先，插件内部最常用的查找原语 |

## 4. 蓝图视角：AS 类 ≈ native 类

蓝图编译管线**没有**为「父类是 AS 类」设专门分支：

```cpp
// [UEENGINE]Engine/Source/Editor/KismetCompiler/Private/KismetCompiler.cpp:604-611
void FKismetCompilerContext::SpawnNewClass(const FString& NewClassName) {
    ...
    NewClass = NewObject<UBlueprintGeneratedClass>(Blueprint->GetOutermost(), ...);
}
```

继承 AS 类的蓝图就是普通 BPGC，`SuperStruct` 直接指向 `UASClass` 实例。
但「完全不关心」不成立：引擎里约 30 处 `AS FIX` 补丁打破了「非 native 的只有 BPGC」的原假设，
全部遵循同一模式——**把 AS 类当 native 类看待**：

| 补丁位置 | 内容 |
|---|---|
| `[UEENGINE].../BlueprintEditorUtils.cpp:943-945` | `FindFirstNativeClass` 加 `bIsScriptClass` 命中——**AS 类是重编译边界**，蓝图 reinstance 只走 BPGC 链 |
| `[UEENGINE].../BlueprintGeneratedClass.cpp:1220` | `UpdateCustomPropertyListForPostConstruction` 找 native 祖先时停在 AS 类 |
| `[UEENGINE].../BlueprintGeneratedClass.cpp:2593` | GC 引用遍历走到 AS 类即停，交给 AS 侧 |
| `[UEENGINE].../BlueprintGeneratedClass.cpp:1413-1418` | `IsFunctionImplementedInScript`：AS 父类实现过的方法**算「已在脚本实现」**——影响蓝图 BlueprintNativeEvent 分发 |
| `[UEENGINE].../Class.cpp:5115`、`UObjectGlobals.cpp:4465/4849` | CDO 构造、属性初始化、子对象回收：AS 类按 native 语义处理 |
| `[UEENGINE].../BlueprintSupport.cpp:310-312` | AS 类有 `CLASS_CompiledFromBlueprint` 但**明确排除**出「这是蓝图包」的判定（蹭 flag 的纠偏） |

> 心智模型：**AS 类在蓝图眼里 ≈ 一个 native C++ 类**。继承、重编译、序列化按 native 边界处理；
> 差异只在 `bIsScriptClass` 让边界判断多一个命中条件，以及热重载时的协调胶水。

## 5. 热重载：reinstancing 全序列（编辑器开发循环）

AS 类改动触发 full reload 时（`[UE]Private/ClassGenerator/AngelscriptClassGenerator.cpp` + `AngelscriptEditor/Private/ClassReloadHelper.cpp`）：

1. **新旧并存**：新 `UASClass` 创建，旧类改名 `XXX_REPLACED_N` + `CLASS_NewerVersionExists`；
2. **扫描全部蓝图找依赖**（`ClassReloadHelper.cpp:73-149`）：`TObjectIterator<UBlueprint>` 遍历内存中所有蓝图，逐节点查外部依赖、逐 Pin 改写指向新 struct/enum/delegate、`FArchiveReplaceObjectRef` 探测类引用——命中即进 `DependencyBPs`。**判定是粗粒度的（有引用即重编译，与成员是否被用到无关）**；
3. **强制 GC**；
4. **走 UE 标准重实例化**：`FBlueprintCompilationManager::ReparentHierarchies(ReloadClasses)`——旧类所有存活实例（Actor、CDO、组件）按新类重建，属性 delta 拷贝迁移；
5. **重编译依赖蓝图**：`RefreshRelevantNodesInBP` + `QueueForCompilation` + `FlushCompilationQueueAndReinstance`；
6. 再 `ForceGarbageCollection` 收尾。

源码注释自嘲该管线是 "hacked-together mess using the old reloader"（UE 新 reload 系统处理不了
UFunction 定义变化，只能用旧管线；`ClassReloadHelper.cpp:19-22`，CVar `angelscript.UseUnrealReload` 可试新系统）。
另有 CDO 传播胶水：AS 父类 CDO 变化须先传播给子蓝图 CDO，否则后续 delta 拷贝断裂
（`[UEENGINE].../BlueprintCompilationManager.cpp:1610-1618`）。

代价：两轮全量 GC + 全实例重建 + 批量蓝图编译，秒级开销，**纯编辑器开发循环设计**。

## 6. 运行时：cooked 构建的双执行模型与 Cache 更新

### 6.1 热重载机制在移动端不存在

```cpp
// [UE]Public/AngelscriptManager.h:12
#define AS_CAN_HOTRELOAD (PLATFORM_DESKTOP)
```

移动端编译期即剔除 `NewerVersion`、reinstance 分支、属性区 +128 松弛、
`#if AS_CAN_HOTRELOAD` 的空指针检查（死代码消除）。`ClassReloadHelper` 整个文件
在 `AngelscriptEditor` 模块，cooked 不打包。

### 6.2 cooked 的脚本来源

```cpp
// [UE]Private/AngelscriptManager.cpp:362-363
bUsePrecompiledData = !bGeneratePrecompiledData
    && !FParse::Param(FCommandLine::Get(), TEXT("as-ignore-precompiled-data"))
    && !IsRunningCommandlet() && !WITH_EDITOR && !bScriptDevelopmentMode;
```

cooked 从 `PrecompiledScript.Cache`（序列化的 AS 字节码 + 模块描述符）加载，
运行时不解析任何 `.as` 源码。启动时 class generator 从 Cache 跑一遍
（`GetModulesToCompile()`，`StaticJIT/PrecompiledData.h:685`，注释 "Serve loaded data
that would normally come from preprocessor"），`UASClass` 按启动时在场的 Cache 生成。

### 6.3 双执行模型与 GUID 降级链

加载点（`AngelscriptManager.cpp:434-480`）：

1. 优先尝试配置特定文件：Shipping/Test/Development 分别找
   `PrecompiledScript_Shipping/Test/Development.Cache`，不存在再退回 `PrecompiledScript.Cache`；
2. **校验只查构建配置，不查脚本版本**：

```cpp
// [UE]Private/StaticJIT/PrecompiledData.cpp:2594-2612
// BuildIdentifier 仅 1/2/3/4 = Debug/Development/Test/Shipping
bool FAngelscriptPrecompiledData::IsValidForCurrentBuild() {
    return BuildIdentifier == GetCurrentBuildIdentifier() && BuildIdentifier != -1;
}
```

3. **关键降级分支**——新 Cache 与二进制内 StaticJIT 转译代码的 GUID 不匹配时：

```cpp
// [UE]Private/AngelscriptManager.cpp:471-477
const FStaticJITCompiledInfo* CompiledInfo = FStaticJITCompiledInfo::Get();
if (CompiledInfo != nullptr && CompiledInfo->PrecompiledDataGuid != PrecompiledData->DataGuid) {
    UE_LOG(Angelscript, Warning,
        TEXT("... does not match the transpiled C++ in the game binary. Transpiled code will not be used!"));
    FJITDatabase::Get().Clear();
}
```

**双层执行模型**：

| 场景 | 类结构来源 | 执行方式 |
|---|---|---|
| 完整打包（默认） | Cache（GUID 匹配） | StaticJIT 转译的本地 C++ |
| **只推新 Cache（脚本热更）** | 新 Cache，启动时重建 UASClass | **AS VM 字节码解释执行** |
| `-as-development-mode` | 现场解析 .as 源码 | 解释执行（设备上开发） |
| 编辑器 | 源码 + 热重载 | JIT/解释 |

解释器是 AS 引擎核心、永远编译在二进制里，不是可选项——这就是「手机可热更脚本、
代价是降级为解释执行」的机制本源。类结构在引擎初始化阶段（任何实例加载之前）重建，
**不需要 reinstancing**，重启 App 生效。

### 6.4 只推 Cache 的限制清单

1. **冷更新，非热替换**：必须重启 App；无运行中换类能力（`AS_CAN_HOTRELOAD` 桌面限定）；
2. **性能降级**：转译代码 → 字节码解释，帧率敏感逻辑要预留余量；
3. **蓝图兼容性无校验**：新 Cache 改了类布局，已序列化的蓝图/关卡资产只靠 UE
   按名匹配的序列化容错（删属性丢数据、改函数签名可能运行时崩）；
   cooked 里没有 `BlueprintCompilationManager` 兜底重编译——**兼容纪律要自查**；
4. **构建配置强绑定**：Cache 的 `BuildIdentifier` 必须与包一致（Shipping 包配 Shipping Cache），
   不匹配则整个丢弃回退（`AngelscriptManager.cpp:457-463`）；
5. 降级只影响执行层，反射层（`UASClass`/`UFunction`/`FProperty`）在两种模式下同构生成。

## 7. 对本 LSP 的影响（交付需求，不在本文展开）

| LSP 能力 | 依赖的本文结论 |
|---|---|
| 父类候选集：AS 类的基类 = C++ native 类 ∪ AS 类，**不含蓝图类**；诊断「不能继承蓝图类」有引擎错误文本可对齐（`Class %s has an unknown super type %s`） | §2 |
| 语义索引 class symbol 带来源枚举（`NativeCpp` / `Angelscript` / `Blueprint`），判定规则与引擎 `bIsScriptClass` 对齐；`.d.as` 全算 native 侧，工程 `.as` 是 Angelscript 侧 | §3.1 |
| 成员查找链跨 AS→native 边界：属性偏移/函数绑定语义与 C++ 父类一致；「解析到 AS 类即可停」对应 `FindFirstNativeClass` | §4 |
| 改动影响分析：可参考 `DependencyBPs` 的粗粒度判定（引用即重编译），LSP 可做得更细（成员级）；引擎错误文本可入诊断码素材 | §5 |
| `.d.as` 作为权威类型源的运行时依据：蓝图侧类型是启动时按 Cache 重建的，源码侧真值在导出声明 | §6.2 |
